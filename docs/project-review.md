# بررسی پروژه peak-forecast

تاریخ بررسی: 2026-09-08 · شاخه: `arena/01a0815c-peak-forecast` (بر پایه commit `bcaf46e`)

## خلاصه اجرایی

یک پروژهٔ شخصی و عملیاتی برای «پیش‌بینی شب‌های پرمسافر + قیمت پیشنهادی هر شب» برای
کلبهٔ خود (سیدکلا، جاجیگا 3297585). وضعیت: از «فاز ایده» عبور کرده و v2 پایپ‌لاین
قابل‌اجرا (collect → forecast → backtest → dashboard → telegram) ساخته و تست‌ها سبز است.
طراحی، داکیومنت و معماری کیفیت بالایی دارند؛ نگرش «جعبهٔ صداقت» (backtest بدون نشت
اطلاعات آینده، تفکیک بلاک میزبان از رزرو واقعی، گاردهای اقتصادی) از نقاط قوت اصلی است.

## وضعیت فنی

- **۲۴ تست پاس** (`pytest tests/ -q`) در ۰٫۱۴ ثانیه — سبز.
- ~۲۰۰۰ خط پایتون + یک داشبورد HTML تک‌فایله (~۴۴۰ خط).
- دادهٔ قابل‌استفادهٔ درون‌ریپو: `persian_holiday.db` (۹٬۴۲۵ رویداد، پوشش ۱۳۷۰→۱۴۲۰)،
  `seasonality.json`، `yearmap-1405/1406.json` (۳۶۵ روز هرکدام، درست از 21-03-2026 تا 20-03-2027).
- وابستگی‌ها: `jdatetime` و `pytest` (در ریپو فایل requirements/پای‌پراجکت وجود ندارد).

### معماری (منطق منسجم سه‌لایه‌ای)
- **داده/موتور** (`src/`): `collector` (دادهٔ خام روزانه از رادار)، `market` (میانه/چندک قیمت
  رقبا + سرعت پرشدن 3d/7d روی همان رقیب‌ها)، `engine` (MDF = S×W×H×R ضربی → DI 0..100 →
  قیمت از میانهٔ رقبا با تعدیل محدود)، `calendar_lib` + `seasonality` + `yearmap` (تقویم جلالی)،
  `floor`/`pricing_rules` (کف اقتصادی)، `ledger`، `backtest`، `pace` (چالش‌گر سایه).
- **Pipeline** (`scripts/`): `run_forecast` → `run_backtest` → `build_dashboard` →
  `tg_digest` + اسکریپت جمع‌آوری/روزانه.
- دیتابیس واحد `peak_forecast.db` با جداول nights / meta / forecast_audit / reservations / decisions.

### نقاط قوت
1. **اعتبارسنجی صادقانه**: بک‌تست فقط شب‌های سررسیده‌شده را با اطلاعاتِ زمانِ صدور ارزیابی می‌کند
   (جلوگیری از نشت آینده — در تست هم پوشش داده شده). متریک تجاری ساختگی/غیرقابل‌اثبات حذف شده.
2. **تفکیک مفهومی بلاک از رزرو** (`docs/block-flag.md`): اتاق خود در pace/backtest همیشه
   exclude می‌شود چون ردیف‌های «پر» ممکن است بستن تقویم باشند نه رزرو.
3. **گاردهای اقتصادی**: کف هزینهٔ تمام‌شده و بررسی `infeasible` وقتی بازار زیر کف است.
4. **قیمت مبتنی بر رقبا نه ضرب خام**: تعطیل را روی قیمت رقیب دوباره ضرب نمی‌کند (تست دارد).
5. **داکیومنت قوی و پر از «چرا»**: IDEA، data-inventory، پلن بهبود، بریف مشورتی، همهٔ تصمیمات
   قفل‌شده با دلیل مستند شده‌اند.
6. **سایه/چالش‌گر**: pace و استخراج متن در shadow mode هستند و تا اثبات BSS≥5% فعال نمی‌شوند.

## مشکلات و ریسک‌های مشاهده‌شده

| اولویت | مورد | توضیح |
|---|---|---|
| کم | منبع دادهٔ جاری در sandbox غایب | مسیرهای `H:/...` جاجیگا این‌جا نیست؛ کد با fallback می‌رود به `data/` و فقط تقویم تعطیلات در دسترس است. `check_sources` در این محیط fail می‌شود (منتظره است). برای اجرای واقعی باید روی ماشین خود کاربر با کرون `daily.sh` اجرا شود. |
| کم | بدون فایل وابستگی | `jdatetime` و `pytest` هیچ‌جا pin نشده‌اند — نصب مجدد/CI شکننده است. پیشنهاد: یک `requirements.txt` ساده. |
| متوسط | `data/seasonality.json` (کامیت‌شده) با کد/منطق ناسازگار | مقدار ماه ۱ (فروردین) = ۰٫۶۴۲ است که با فرض «فروردین=پیک نوروز» (و مقادیر EXPERIMENTAL و نمودار دیداری سال‌نما) در تضاد است. جالب: `run_forecast` این فایل را اصلاً نمی‌خواند (هر بار از corpus بازمی‌سازد)؛ یعنی فایل مرده/گمراه‌کننده است یا متعلق به نگاشت/دورهٔ دیگری است. باید تأیید و هم‌راستا یا حذف شود. |
| متوسط | هماهنگی روز-هفته | `engine.WEEKDAY_W` (Thu=1.30, Fri=1.12) با «پنجشنبه شب پرمیوم‌ترین» هماهنگ است، اما `is_weekend` و `DOW_TIER` در جاهای مختلف باید یک‌دست باشند (پنجشنبه-جمعه). وارسی دستی پیشنهاد می‌شود، چون چند جدول معادل موازی وجود دارد. |
| اطلاع | قیمت از `P50 رقبا × تعدیل` و نه ضرب تعطیل | این یک تصمیم مستند و آزمایشی است؛ مقدار `quality_adj` و آستانه‌ها هنوز اعداد دستی/ابتدایی‌اند و «بک‌تست قیمت معامله» عمداً غیرفعال است چون مبلغ واقعی رزرو ثبت نشده. |
| اطلاع | v1.1 فازبندی‌شده ولی هنوز کامل اجرا نشده | پلن `v1.1-improvement-plan.md` مواردی را وعده می‌دهد (مثلاً ladder روی CDF واقعی، min_stay پویا، orphan) که در کد فعلی `pricing_rules.ladder_multiplier` به‌عمد «خنثی=۱٫۰۰» بازگشته است. این «ساده‌سازی آگاهانه» است اما در README/NOTE جا باز بماند تا گمراه نشود. |

## قدم بعدی پیشنهادی

1. **کپیِ فایل دادهٔ واقعی (radar_history.db + corpus + own_bookings) روی این ماشین/CI** تا
   `check_sources` و کل پایپ‌لاین با دادهٔ واقعی دیده شود، یا یک موک سبز برای مسیرهای خارجی.
2. افزودن `requirements.txt`.
3. روشن‌کردن تکلیف `data/seasonality.json` (حذف یا تصحیح).
4. سپس اجرای مرحله‌به‌مرحلهٔ پلن v1.1 (که مستند و آمادهٔ اجراست).

> این فقط «بررسی» است و هیچ تغییری در کد ایجاد نکرده‌ام (working tree تمیز، فقط این فایل بررسی اضافه شده).
